# 기술 스택 및 검증 기준

> 상태: Lab 웹 기준선 확정<br>
> 기준일: 2026-08-03<br>
> 기준 저장소: [aigemro/dream-bike-garage](https://github.com/aigemro/dream-bike-garage)

이 문서는 메인 게임에 현재 적용된 기술과 앞으로 Lab에서 검증할 기술을 구분합니다. 아직 결정되지 않은 항목은 확정된 것처럼 구현하지 않습니다.

## 1. 현재 메인 프로젝트 구성

| 영역 | 현재 기술/구성 | 상태 | 근거 |
|---|---|---|---|
| 언어 | TypeScript 5.8 | 적용 | 게임 코드와 도메인 규칙 |
| 게임 엔진 | Phaser 3.90 | 적용 | Canvas 렌더링, Scene, 드래그 입력 |
| 빌드 도구 | Vite 7 | 적용 | 개발 서버와 정적 빌드 |
| 패키지 관리 | npm | 적용 | `package-lock.json`, `npm ci` |
| 테스트 | 자동화 테스트 미도입 | 예정 | 도메인 규칙 분리 시 Vitest 도입 검토 |
| 웹 UI | HTML/CSS + Phaser Canvas | 적용 | React 등 UI 프레임워크는 현재 사용하지 않음 |
| 화면 기준 | 390 × 810, Phaser Scale FIT | 적용 | 모바일 세로 화면 우선 |
| 배포 | GitHub Actions + GitHub Pages | 적용 | `main` 반영 시 테스트·빌드·배포 |
| 런타임 | Node.js 20.19 이상 | 적용 | 개발 및 CI 빌드 환경 |
| 모바일 패키징 | 미적용 | 재검토 | 기존 문서에는 Capacitor 검토가 있으나 앱인토스 우선 전략과 비교 필요 |
| 백엔드/API | 없음 | 미정 | 현재 MVP는 정적 웹 게임 |
| 사용자 로그인 | 없음 | 미정 | 앱인토스 연동 방식 검증 필요 |
| 저장 방식 | 영구 저장 미적용 | 미정 | 로컬 저장과 서버 저장 범위 결정 필요 |
| 결제/광고 | 없음 | 미정 | 앱인토스 SDK 실험 대상 |
| 분석/오류 수집 | 없음 | 미정 | 출시 전 도구 선정 필요 |

## 2. 현재 코드 구조

- `src/game`: Phaser 설정과 Scene, 화면 입력·렌더링
- `src/domain`: 보드, 머지, 주문, 조립 등 순수 게임 규칙
- `src/data`: 아이템과 밸런스 정적 데이터
- `src/ui`: DOM UI와 스타일
- `tests`: 프레임워크와 분리한 도메인 단위 테스트
- `docs/game-design`: 게임 기획 명세
- `docs/development`: 기술 설계 문서

Phaser Scene이 입력과 렌더링을 맡고, 게임 규칙은 Phaser에 의존하지 않도록 분리하는 현재 방향을 유지합니다. 이 구조는 WebView 환경 테스트와 단위 테스트에 유리합니다.

## 3. 목표 플랫폼

### 1차: 웹 MVP

- 브라우저와 GitHub Pages에서 핵심 머지 루프 검증
- 마우스와 모바일 터치 입력 지원
- 세로 화면 우선
- 빠른 배포와 기획 검토

### 2차: 앱인토스 출시 검증

앱인토스는 WebView 기반 SDK를 제공하므로 현재 웹 기술 스택을 우선 유지하고, Lab에서 실제 제약과 SDK 호환성을 검증합니다. 앱인토스 기능과 요구사항은 변경될 수 있으므로 구현 시점의 공식 개발자 문서를 다시 확인합니다.

- 공식 개요: https://developers-apps-in-toss.toss.im/intro/overview.html
- API/SDK: https://developers-apps-in-toss.toss.im/documentation
- 릴리스 노트: https://developers-apps-in-toss.toss.im/release-note

앱인토스가 우선 출시 경로라면 Capacitor는 당장 기본 스택으로 확정하지 않습니다. Google Play 또는 독립 앱 패키징이 실제 범위에 들어올 때 별도 비교합니다.

## 4. Lab 우선 실험

| 우선순위 | 실험 | 확인 내용 | 성공 기준 |
|---|---|---|---|
| P0 | Toss WebView 최소 실행 | Vite + Phaser 빌드 실행, SDK 초기화 | 앱인토스 테스트 환경에서 첫 화면과 게임 Canvas가 정상 표시됨 |
| P0 | 화면/입력 | 터치 드래그, 다양한 화면 크기, Safe Area | 핵심 조작이 잘리거나 오입력 없이 동작함 |
| P0 | 앱 라이프사이클 | 백그라운드/복귀, 새로고침, 뒤로가기 | 게임 상태 손실과 비정상 종료 처리 기준이 정리됨 |
| P0 | 저장 | localStorage/IndexedDB/서버 저장 비교 | 비로그인·로그인 상태별 저장 정책을 결정할 수 있음 |
| P1 | 앱인토스 로그인 | 사용자 식별과 세션 처리 | 필요한 서버 구성과 개인정보 범위를 문서화함 |
| P1 | 인앱 결제 | 상품 조회·구매·복구·오류 흐름 | 테스트 결제와 중복 지급 방지 흐름을 검증함 |
| P1 | 광고 | 보상형/전면형 광고와 게임 복귀 | 보상 지급 및 실패 처리가 중복 없이 동작함 |
| P1 | 성능 | 초기 로딩, 메모리, 에셋 크기 | 목표 기기와 네트워크 기준을 정하고 측정 결과를 기록함 |
| P2 | 운영 | 분석, 오류 수집, 원격 설정 | 최소 운영 데이터와 동의 범위를 결정함 |
| P2 | 일반 앱 패키징 | Capacitor 등 대안 비교 | 앱인토스 외 배포가 필요할 때만 채택 여부를 결정함 |

## 5. 제안하는 기술 원칙

1. 현재 MVP에서는 TypeScript + Vite + Phaser를 유지합니다.
2. React는 관리 화면이나 복잡한 DOM UI 요구가 생기기 전까지 추가하지 않습니다.
3. 게임 규칙은 Phaser와 앱인토스 SDK에서 분리해 브라우저에서도 테스트 가능하게 합니다.
4. 앱인토스 API 호출은 `platform` 어댑터로 감싸 웹 모의 구현과 실제 SDK 구현을 교체할 수 있게 합니다.
5. 결제 보상과 중요 재화는 클라이언트만 신뢰하지 않습니다. 결제를 채택하면 서버 검증과 중복 지급 방지를 함께 설계합니다.
6. Lab 결과가 성공한 뒤 메인 저장소에 별도 Issue/PR로 다시 반영합니다.

권장 경계 예시:

```text
domain (게임 규칙)
  ↑
game/application (게임 흐름)
  ↑
platform adapter
  ├─ browser mock
  └─ apps-in-toss SDK
```

## 6. 아직 결정이 필요한 기준

아래 항목은 코드만으로 확정할 수 없습니다.

1. **최초 출시 채널**: 앱인토스 우선인지, 웹과 앱인토스를 동시에 운영할지
2. **계정 정책**: 비로그인 플레이를 허용할지, 토스 로그인/식별이 필수인지
3. **저장 범위**: 기기 로컬 저장만 사용할지, 계정 기반 서버 저장을 제공할지
4. **수익 모델**: 인앱 결제, 보상형 광고, 두 방식 병행, 또는 MVP에서는 제외할지
5. **백엔드**: 필요한 경우 어떤 언어·호스팅·DB를 사용할지
6. **지원 기기 기준**: 최소 화면 크기와 목표 토스 앱/OS 버전
7. **오프라인 정책**: 네트워크 없이 플레이 가능한 범위와 동기화 충돌 처리
8. **출시 외 플랫폼**: 추후 Google Play/iOS 독립 출시까지 준비할지

이 기준이 정해지면 ADR(`docs/decisions/`)로 확정하고 Lab 실험 순서를 세분화합니다.

## 7. 실행 및 배포 기준
