# B안 · 활성 플레이 시간 + 계정별 진행

## 검증 가설

Day 제한은 실제 시계가 아니라 사용자가 게임 화면에서 플레이하는 시간에만 차감해야 짧은 세션의 긴장감과 중단 복귀의 안전성을 함께 제공할 수 있다. 계정과 게임 프로필을 분리하고 진행 상태를 `playerId` 단위로 저장하면 같은 기기에서 계정을 전환해도 각 사용자의 Day·재화·주문·컬렉션·성장을 독립적으로 복원할 수 있다.

## 이번 구현

- 비밀번호를 수집하지 않는 테스트 계정 A/B 로그인
- 최초 로그인 시 닉네임 기반 게임 프로필 생성
- Day 규칙을 순수 모듈(`day-session-rules.ts`)로 분리하고 단위 테스트로 검증
- Lab 기본 10초 Day와 헤더의 `Day 10초/1분/3분` 길이 전환(다음에 시작하는 Day부터 적용)
- 준비·진행·일시정지·마감·정산 상태. 시간이 끝나면 새 입력을 막고 정산 (2026-10-09부터 작업대는 머지 코어 E v3. 납품을 행동 시점에 확정하므로 마감 대기가 필요 없음. 이전 C안에서는 장착 연출 중 납품을 최대 3초 기다림)
- 작업대(E v3 보드·알바 체력·주문 진행)는 계정별로 저장되어 다음 Day에 이어짐
- 홈·플레이의 390×810 게임 캔버스 내부에 현재 Day, 남은 시간(mm:ss), 오늘 수입 표시. 홈에는 일시정지 사유도 표시
- 플레이 HUD의 큰 타이머·남은 시간 막대·종료 임박(Day 길이 10%, 최소 3초) 색상 표시
- 백그라운드, 화면 이탈, 로그아웃 시 타이머 일시정지와 자동 저장. 새로고침으로 다시 열면 진행 중이던 Day는 일시정지로 복원
- 시간 종료 또는 Lab용 `DAY 종료` 버튼을 통한 한 번만 적용되는 정산과 오늘 수입 확인
- 자전거 납품 후 별도 보상 화면 없이 보드 부품을 유지한 채 다음 주문 즉시 시작. 주문 3종 순환, 주문 메타 급여 지급, 납품 자전거 이해도 반영
- 계정별 컬렉션(이해도·등록·제작·전시)과 자전거 성장 저장. 도감·전시·성장 화면이 로그인한 계정의 진행을 사용
- Lab 외곽 헤더는 오디오·Day 길이·수동 Day 종료·로그아웃 등 검증 도구만 유지
- Day 시작·정산 패널은 최대 318px, 계정 진행 패널은 최대 330px로 제한하고 정보 카드를 2열로 압축
- 계정 화면은 저장된 14일 기록 중 최근 3일만 요약해 내부 스크롤 없이 게임 캔버스 안에 표시
- Day HUD와 주문 카드 사이에 8px 간격을 두어 타이머 막대와 주문 경계를 분리
- Day 시작 준비 화면에 대회 주기(5일)에 맞춘 한 줄 공방 달력 표시 — 대회일·오늘 강조와 다음 대회 D-day 안내 (#231 후속)

## 체험 순서

1. 계정 A로 로그인하고 게임 닉네임을 만든다.
2. 헤더의 `Day 10초` 버튼으로 측정할 Day 길이를 고른다(10초 → 1분 → 3분).
3. `PLAY`에서 Day를 시작하고 주문 또는 수동 Day 종료를 진행한다. 장착 연출 중 시간이 끝나는 경우 그 납품이 오늘 수입에 포함되는지 확인한다.
4. 성장 화면에서 강화한 뒤 다른 화면으로 나갔다 돌아와 강화 단계가 유지되는지 확인한다.
5. 로그아웃한 뒤 계정 B로 별도의 프로필과 진행을 만든다.
6. 계정 A로 다시 로그인해 이전 Day·재화·컬렉션·성장이 복원되는지 확인한다.
7. 플레이 도중 탭을 백그라운드로 보내 남은 시간이 줄지 않는지 확인한다.

## 비교 기준

- A안: 실제 시각 기준 마감 — 복귀 시 시간이 계속 흐르지만 이탈 페널티가 큼
- B안: 활성 플레이 시간 — 중단 복귀가 안전하고 MVP 테스트에 적합함
- C안: 행동 횟수 기준 — 시간 압박은 약하지만 밸런스와 규칙 설명 비용이 큼

## 프로토타입 경계

이번 Lab은 인증·세션·Day·계정별 저장 계약을 검증한다. 실제 Apps-in-Toss 인증과 서버 동기화는 `AuthProvider` 및 저장소 인터페이스의 후속 구현으로 남긴다. 현재 연결된 작업대(C안 택배 화면)는 보드를 저장하지 않으므로 Day가 바뀌면 보드가 비워지며, 주문 번호와 보상·컬렉션·성장 상태만 이어진다. 보드 이월은 머지 코어 채택 후 그 저장 방식에 맞춰 정한다.

상세 계약과 테스트 시나리오는 `docs/DAY_ACCOUNT_EXPERIMENT.md`, 메인 적용 방안은 `docs/DAY_SESSION_MAIN_APPLICATION.md`에 기록한다.
