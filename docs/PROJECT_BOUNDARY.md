# Lab과 메인 프로젝트 운영 경계

## 목적

Dream Bike Garage Lab은 완성 게임을 직접 결정하는 저장소가 아니라, 메인 프로젝트의 기획·설계 질문에 답할 수 있도록 **기술 대안을 개발·비교·검증하는 실험 저장소**입니다.

- 메인 프로젝트: 기획·설계, 기술안 선택, 최종 게임 적용
- Lab: 기술 설계, 다중 프로토타입 구현, 비교 실험, 검증 결과 제공

## Lab에서 다루는 작업

다음 작업은 Lab 이슈로 관리합니다.

- 같은 게임 코어를 구현하는 여러 기술·상호작용 방안
- 조작감, 반복 재미, 성능 또는 유지보수성 비교
- 마우스·터치·반응형 화면·Safe Area 검증
- localStorage·IndexedDB·서버 저장 방식 비교
- 앱인토스 WebView와 SDK 호환성 검증
- 실패 가능성이 있거나 실제 실행 결과가 있어야 판단할 수 있는 기술 질문

Lab에서는 `[실험]`, `[기술]`, `[검증]`이 드러나는 제목을 사용합니다.

## Lab에서 결정하지 않는 작업

다음 항목은 메인 프로젝트에서 먼저 정의하거나 최종 결정합니다.

- 게임 콘셉트와 핵심 플레이 경험
- 머지, 주문, 조립, 수집, 성장의 최종 규칙
- 콘텐츠, 보상, 밸런스 정책
- 화면에 필요한 정보와 사용자 흐름
- 어떤 Lab 결과를 채택할지에 대한 제품 결정
- 출시 가능한 최종 코드와 에셋 적용

기획 질문이 확정되지 않았다면 Lab에서 임의로 게임 규칙을 확정하지 않고 연결된 메인 이슈에 질문을 남깁니다.

## 표준 실험 흐름

1. 메인 이슈에서 기획 의도, 제약, 검증 질문과 평가 기준을 받습니다.
2. Lab 이슈에서 비교할 대안과 공통 초기 조건을 정의합니다.
3. 각 대안을 독립 프로토타입과 URL로 구현합니다.
4. 같은 시나리오로 조작감, 명확성, 성능, 확장성 등을 기록합니다.
5. 채택, 조건부 채택, 보류, 폐기 권고와 그 근거를 작성합니다.
6. 결과를 연결된 메인 이슈에 전달합니다.
7. 최종 선택과 제품 적용은 메인 프로젝트에서 진행합니다.

## Lab 이슈 필수 항목

- 연결된 메인 기획·설계 이슈
- 해결하려는 기술 질문
- 실험 가설
- 비교할 대안
- 공통 조건과 평가 항목
- 실행 방법과 독립 URL
- 측정 결과와 관찰 메모
- 각 대안의 장점, 한계, 위험
- 권고 결과: 채택 / 조건부 채택 / 보류 / 폐기
- 결과를 반영할 메인 적용 이슈

## 대표 예시

### 머지 코어

- 메인 질문: 주문 제작에 가장 잘 맞고 캐주얼함을 유지하는 머지 규칙은 무엇인가?
- Lab 실험: 자유 보드형, 주문 중심형, 체인·콤보형을 실행 가능한 형태로 비교
- Lab 결과: 조작 난도, 주문 연결성, 반복 재미, 확장성과 구현 위험 기록
- 메인 후속: 채택안 결정 및 최종 게임 적용

### 저장

- 메인 질문: 어떤 진행 데이터가 언제까지 보존되어야 하는가?
- Lab 실험: localStorage, IndexedDB, 서버 저장의 용량·복구·WebView 제약 비교
- 메인 후속: 제품 정책에 맞는 방식 선택 및 적용

## 프로토타입과 메인 코드의 관계

- 실험 코드는 빠른 비교와 재현성을 우선합니다.
- 검증 전 코드를 공용 모듈로 성급히 통합하지 않습니다.
- 채택된 결과도 메인 저장소에 그대로 복사하는 것을 기본으로 하지 않습니다.
- 메인 프로젝트의 아키텍처, 데이터 정책, 테스트와 품질 기준에 맞게 재구현합니다.
- 실패한 실험도 원인과 배운 점을 남깁니다.

## 완료 기준

Lab 이슈는 단순히 프로토타입이 실행된다고 완료되지 않습니다. 다음 조건을 모두 만족해야 합니다.

- 비교 대상이 같은 조건에서 실행 가능함
- 결과와 한계가 문서화됨
- 권고안과 선택 근거가 있음
- 메인 이슈에 결과가 전달되고 양방향 링크가 남음
