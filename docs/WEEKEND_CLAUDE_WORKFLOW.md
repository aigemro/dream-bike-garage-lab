# 주말 Claude 고토큰 작업 운영안

> 대상: Dream Bike Garage Lab 주말 집중 작업
>
> 준비: 목요일·금요일 / 실행: 토요일 오전 1회 + 오후 1회
>
> 권장 모델: Fable UltraCode 등 장시간 구현·검증에 적합한 모델
>
> 문서 성격: 매주 반복해서 사용하는 작업 선정·요청·검증 기준

## 1. 운영 목표

주말에 남은 토큰을 소진하는 것이 목적이 아니라, 평일에 범위를 미리 좁혀 토요일 두 번의 5시간 세션에서 **독립적으로 검토·병합할 수 있는 결과물**을 남기는 것이 목적이다.

Dream Bike Garage의 현재 최우선 목표는 새 기능을 넓히는 것이 아니라 다음 출시 MVP 흐름을 하나로 연결하고 검증하는 것이다.

> 고객 주문을 확인하고 → 부품을 택배로 수급하고 → 동일 종류·레벨 부품을 2-to-1로 머지하고 → 고객 자전거를 조립·납품하고 → 받은 급여로 내 드림 바이크를 성장시키고 → 앱을 다시 열어도 다음 주문을 이어서 플레이한다.

주말 작업은 이 흐름의 완성도, 자동 검증, 모바일 안정성에 직접 기여하는 항목을 우선한다. 실제 브랜드, 매치3, 레이스, 복잡한 경영, 광고·결제, 서버 계정은 별도 합의 전까지 주말 집중 작업에 넣지 않는다.

## 2. 5시간 제한을 고려한 기본 원칙

1. 토요일 오전·오후 작업은 각각 단독 PR로 끝낼 수 있게 나눈다.
2. 한 세션에는 주목표 1개와 시간이 남을 때 수행할 보조목표 1개만 넣는다.
3. 구현, 전 범위 리팩터링, 시각 개선을 한 요청에 섞지 않는다.
4. 먼저 현재 `main`, 열린 이슈, 기존 트랙과 중복 여부를 확인하게 한다.
5. 5시간 안에 완성하기 어렵다면 범위를 임의로 넓히지 말고 완료된 부분·미완료 부분·후속 요청문을 남기게 한다.
6. 빌드 성공만으로 완료하지 않는다. 핵심 상태 전이, 모바일 화면, 저장·복구를 작업 성격에 맞게 검증한다.
7. 기존 사용자 변경을 덮어쓰거나 관련 없는 파일을 정리하지 않는다.
8. PR은 한 가지 목적만 설명하고 관련 이슈, 확인 경로, 테스트 결과, 남은 위험을 포함한다.

## 3. 목요일: 후보 수집과 범위 결정

목요일에는 구현을 시작하지 않고 다음 주말 후보를 모은다.

### 확인할 자료

- 최신 `main`과 최근 병합 PR
- 열린 이슈 및 GitHub Actions 실패 여부
- `docs/MVP_READINESS_PLAN.md`
- `docs/LAB_PROTOTYPE_MAP.md`
- `docs/TRACK_CLASSIFICATION.md`
- 최근 사용자 화면 피드백과 목요일 기획 협의 결과

### 후보 분류

- **작업**: 구현이 필요하고 완료 조건을 코드·화면으로 판정할 수 있음
- **검토**: 설계 충돌, 중복 구현, 트랙 경계, 채택 후보 비교가 필요함
- **테스트**: 이미 구현됐지만 완주·복구·모바일·회귀 증거가 부족함
- **보류**: 기획 결정, 실기기, 외부 권한 또는 에셋이 없으면 진행할 수 없음

### 후보 점수

각 후보를 0~2점으로 평가한다.

| 기준 | 0점 | 1점 | 2점 |
|---|---|---|---|
| MVP 기여 | MVP 이후 | 간접 기여 | 핵심 루프·출시 판정 직접 기여 |
| 준비도 | 기획 결정 필요 | 일부 불명확 | 입력·완료 조건 명확 |
| 독립성 | 여러 선행 작업 필요 | 일부 의존 | 단독 PR 가능 |
| 검증 가능성 | 판단 방법 없음 | 수동 확인 가능 | 자동 또는 재현 가능한 확인 가능 |
| Claude 적합성 | 단순 소수정 | 보통 구현 | 넓은 코드 추적·테스트·리팩터링 필요 |

합계가 높은 작업을 우선하되, 긴 구현은 오전에, 그 구현의 회귀·수정은 오후에 둔다. 동점이면 출시 MVP의 끊긴 연결을 먼저 해결한다.

### 목요일 산출물

- 오전 후보 1개, 오후 후보 1개
- 각 후보의 관련 이슈와 수정 예상 파일
- 하지 않을 범위
- 성공 조건과 확인 경로
- 기획자에게 확인해야 할 질문

## 4. 금요일: 실행 가능한 요청문으로 확정

금요일에는 최신 `main`을 다시 확인하고 후보를 실제 요청문으로 바꾼다.

### 시작 전 체크

- [ ] 선행 PR이 모두 병합됐는가?
- [ ] GitHub Actions가 정상인가?
- [ ] 같은 작업을 수행하는 열린 PR 또는 브랜치가 없는가?
- [ ] 관련 이슈의 최신 코멘트가 요청문에 반영됐는가?
- [ ] 오전 작업이 오후 작업의 필수 선행 조건인가?
- [ ] 각 세션이 5시간 안에 축소 종료 가능한가?
- [ ] 브랜치명, PR 제목, 관련 이슈가 정해졌는가?

### 세션별 범위표

| 항목 | 토요일 오전 | 토요일 오후 |
|---|---|---|
| 역할 | 주기능 구현·통합 | 테스트·회귀 수정·정리 |
| 필수 목표 | 1개 | 1개 |
| 보조 목표 | 시간이 남을 때 1개 | 시간이 남을 때 1개 |
| 금지 | 전면 디자인 변경, 무관한 리팩터링 | 신규 대형 기능 추가 |
| 종료 산출물 | 코드·문서·검증·Draft PR | 테스트 증거·수정·별도 Draft PR |

오전 작업이 실패해도 오후 요청이 무효가 되지 않도록, 오후 요청에는 다음 분기를 미리 적는다.

- 오전 PR이 준비됨: 해당 브랜치 또는 PR을 기준으로 검증·수정
- 오전 PR이 미완료: 최신 `main`에서 기존 MVP 흐름의 회귀 테스트와 독립 수정 수행

## 5. 현재 기준 우선 작업 백로그

아래 순서는 2026-08-22 기준이다. 매주 목요일 최신 상태를 확인해 완료된 항목은 제거하고 순서를 다시 매긴다.

### P0 — 출시 MVP의 끊긴 연결

1. **출시 수직 슬라이스 완성**

   현재 통합 데모의 주문·택배·머지·자동 장착 이후에 납품, 급여 누적, 내 드림 바이크 성장, 다음 주문 진입을 실제 상태로 연결한다. 디자인 시안만 이어 붙이지 말고 상태 계약과 화면 전환을 정의한다.

2. **초기 주문 3종 연속 완주와 반복 주문**

   로드·MTB·그래블 등 가상 주문 3종을 학습 순서로 구성하고, 세 번째 주문 후에도 다음 주문이 생성되게 한다. 주문 데이터와 보드 유지·초기화 규칙을 검증한다.

3. **첫 플레이 안내와 진행 불가 복구 결합**

   안내 오버레이를 실제 첫 주문 상태와 연결한다. 빈 칸 부족, 잘못된 머지, 필요한 부품 부족, 장착 중 입력 같은 상황에서 원인과 복구 수단을 제공한다.

4. **통합 저장·복구 적용**

   보드, 현재 주문, 장착 상태, 코인, 드림 바이크 성장, 튜토리얼 상태를 하나의 버전 계약으로 저장한다. 새로고침·백그라운드·재진입·손상 데이터 복구를 확인한다.

### P1 — 출시 판정에 필요한 검증

5. **핵심 루프 자동 테스트 기반**

   UI와 분리 가능한 주문·머지·보상·성장 상태 전이를 테스트 가능하게 정리하고, 첫 주문과 3종 반복, 저장 직렬화·복구, 잘못된 입력을 자동 검증한다. 테스트 도입 자체보다 회귀를 잡는 대표 시나리오를 우선한다.

6. **390×810 모바일·Safe Area 회귀 검증**

   타이틀 → 홈 → 게임 → 정산 → 성장 → 홈 흐름에서 잘림, 겹침, 스크롤, 최소 터치 영역, 뒤로가기와 복귀를 점검한다. 가로 브라우저용 화면을 출시 흐름에 혼합하지 않는다.

7. **전체 흐름 시각 회귀 점검**

   대표 상태별 스냅샷을 만들고 자전거·부품 공용 모듈, 주문 진행률, 장착 전후 표현, 정산 수치, 다음 주문 카드의 회귀를 확인한다.

8. **앱인토스 WebView 준비도 검토**

   현재 공식 기준을 다시 확인해 라이프사이클, Safe Area, 뒤로가기, 오디오 복귀, 저장 시점, 배포 설정을 체크한다. 실기기 없이는 판정할 수 있는 항목과 없는 항목을 분리한다.

### P2 — P0/P1 이후

9. 비교가 끝난 트랙의 결과 문서와 메인 이관 후보 정리
10. 임시 에셋·문구의 권리와 출처 목록화
11. 로딩·설정·오디오의 실제 기능 연결
12. 초기 10레벨 데이터와 난이도·경제 측정 도구

### 당분간 토큰을 쓰지 않을 항목

- B/C 시안을 모두 구현하는 것 자체가 목적인 화면 증식
- 실제 글로벌 브랜드·실제 모델·팀 에디션
- 매치3, 레이스, O2O, 매장 경영
- 광고·결제·에너지·시즌 패스
- 최종 밸런스 수치 확정
- 메인 이관 기준이 없는 대규모 공통화·전면 재작성

## 6. 권장 토요일 구성

### 오전 세션 — 깊은 구현·통합

권장 1순위는 P0에서 아직 완료되지 않은 가장 앞 항목이다.

진행 순서:

1. 최신 `main`, AGENTS.md, 관련 이슈·문서·최근 PR 확인
2. 중복·충돌·선행 조건 보고
3. 최소 설계와 수정 범위 제시
4. 구현
5. 빌드 및 핵심 시나리오 검증
6. 문서와 프로토타입 지도 갱신
7. Draft PR 생성

오전 완료 기준은 “코드가 많음”이 아니라 사용자가 한 단계 더 완주할 수 있고, 그 상태 전이가 재현 가능하게 검증된 것이다.

### 오후 세션 — 적대적 테스트·수정

오후에는 오전 결과 또는 최신 `main`을 새로 검토하는 시선으로 검사한다.

검증 렌즈:

- 정상 경로: 첫 주문부터 다음 주문까지 완주
- 경계 상태: 보드 빈 칸 0~1개, 목표 초과 부품, 빠른 연속 입력
- 복귀: 새로고침, 백그라운드, 화면 왕복, 저장 데이터 손상
- 화면: 390×810, Safe Area, 긴 한글 문구, 버튼 최소 영역
- 회귀: 기존 트랙 진입, Phaser 인스턴스 정리, GitHub Pages base 경로
- 코드: 중복 상태, 죽은 코드, 화면 전용 상수와 규칙 데이터 혼합

오후에는 발견한 문제를 우선순위별로 고치고, 범위를 벗어난 문제는 재현 절차와 후속 이슈 문안으로 남긴다.

## 8. Claude 요청 템플릿 — 토요일 오후

```text
Dream Bike Garage Lab 저장소의 주말 오후 검증·수정 작업을 진행해줘.

[검증 기준]
- 오전 결과: {PR 또는 브랜치 링크. 없으면 최신 main}
- 핵심 시나리오: {첫 주문 완주, 3종 반복, 저장 복구 등}
- 기준 화면: 모바일 세로 390×810

[필수 검증]
1. 정상 흐름을 처음부터 끝까지 재현
2. 경계 입력·보드 막힘·화면 왕복·저장 복구 확인
3. 기존 트랙과 GitHub Pages 빌드 회귀 확인
4. 화면 겹침·잘림·스크롤·터치 영역 확인

[처리 원칙]
- 재현된 P0/P1 문제는 범위 안에서 수정
- 큰 구조 변경이나 새 기능은 구현하지 말고 후속 이슈 문안으로 분리
- 테스트가 없어서 회귀 위험이 큰 상태 전이는 최소 자동 테스트 추가
- 오전 구현을 그대로 신뢰하지 말고 상태·화면·코드 세 관점에서 독립 검토

[완료 조건]
- 발견 사항을 심각도와 재현 절차로 정리
- 수정 전후 결과와 실행한 명령 기록
- npm run build 및 추가한 테스트 통과
- 별도 Draft PR 생성. 오전 브랜치에 종속되면 그 사실과 병합 순서를 명확히 표시
- 남은 실기기·기획 의존 항목 분리
```

## 9. 세션 종료 보고 형식

Claude에게 아래 형식을 지키게 하면 다음 요청을 만들기 쉽다.

```text
1. 완료한 목표
2. 사용자 관점에서 달라진 흐름
3. 변경 파일과 핵심 상태 계약
4. 실행한 검증과 결과
5. 발견했지만 범위 밖이라 남긴 문제
6. 기획 또는 실기기 확인이 필요한 항목
7. PR 링크와 병합 순서
8. 다음 5시간 세션에 그대로 붙여 넣을 요청문
```

## 10. 주말 완료 판정

- [ ] 오전·오후 각각 독립적인 결과 또는 명확한 의존 관계가 남았다.
- [ ] 관련 이슈와 Draft PR이 연결됐다.
- [ ] 빌드 이외의 핵심 시나리오 검증 증거가 있다.
- [ ] 모바일 세로 화면 영향을 확인했다.
- [ ] Lab의 비교 실험과 메인의 최종 결정 경계를 지켰다.
- [ ] 미완료 항목이 숨겨지지 않고 다음 요청문으로 남았다.
- [ ] 실제 브랜드·출시 이후 기능으로 범위가 새지 않았다.
